# 從想法到上線的工作流（通用版）

> 用途：所有專案共用的抽象工作流程，之後會改寫成一組 skill（以 mattpocock/skills 為骨架）。
> 依據：mattpocock/skills 的主流程，以及實際專案裡用過的做法。
> 專案相關的細節（指令、代理權重、實測方式、部署）不寫在這裡，改寫在各專案的**專案層**（見第 2 節）。
> 2026-11-26 起草，2026-11-27 定稿並開始照著改寫 skill。

---

## 0. 總覽

使用者關心的是四大塊，技術細節（測試、Git、worktree、檢查指令）一律由 AI 在背景處理，使用者不需要規劃、也不用記指令。

| 大塊 | 使用者會用到的指令 | 使用者會看到什麼 |
|---|---|---|
| 1. 規劃（研究、解釋） | `/askme`、`/brainstorm`、`/explain`、`/research`、`/to-plan` | 提問卡、點子清單、說明、研究結論、規劃文件 |
| 2. 審查 | `/plan-review` | 必修清單，以及「下次再說」清單 |
| 3. 實作成果 | `/implement-plan` | 每批一份 HTML 成果報告 |
| 4. 下次如何改進 | `/retro`、`/health-check` | 依嚴重程度排序的改進建議；程式碼健康檢查的 HTML 報告 |

不知道該用哪個指令時，打 `/which`，它照這四大塊告訴你下一步。

完整的流程：

```
            ┌──────────── 匝道 ────────────┐
            │ 超大模糊專案 → /wayfinder     │
            │ 別人開的 issue → /triage      │
            │ 難纏 bug → diagnosing-bugs   │
            └──────────────┬───────────────┘
                           ▼
 對齊 ──► 研究 ──► 規劃 ──► 展開狀態 ──► 拆批次 ──► 每批一輪 ──► 回顧
/askme    research  /to-plan  /expand-    /to-batches  契約→實作→      /retro
          (多輪)              states                   審查→檢查→實測
   ▲         │                                          │
   └─ 原型 ◄─┘（prototype，答不出來的設計問題）         └─► 提交／發布（只在你要求時）
```

第 1 到第 5 步（對齊到拆批次）盡量在**同一個對話**裡做完，不要中途 `/compact`，讓訪談、規格、工單建立在同一份思考上。從第 6 步開始，每一批工作可以換新的對話或交給子代理。

## 1. 全程規則

1. **技術取捨自己定**：架構、門檻、順序、預設值、要不要多測，主代理決定之後直接做，回覆裡說「我直接定了」，並寫進規劃文件的「主代理自定」清單。
2. **只有四類事情停下來問**：提交、發布、改變目標（包含改動使用者原文件指定的來源）、無法復原的動作。
3. **問的時候一律用提問卡**（Claude Code 的 `AskUserQuestion`）：
   - 一張卡最多 4 題，每題 2–4 個選項，推薦選項放第一個並標 `(Recommended)`
   - 問題用動詞開頭、用使用者的詞，約 12 個字
   - 每個選項寫一句「選了會怎樣」，不寫優劣；推薦理由放數字
   - 題目要能獨立看懂，因為出卡時使用者可能看不到前文
4. **出卡就停下來等**：不先假設答案往下做，避免猜錯之後重做、浪費 Token。
   - **時機**：在要動手做依賴這個答案的工作**之前**問，不要做到一半才問
   - **合併**：同一個階段要問的題目盡量放在同一張卡，不要一題一題零散地跳出來
   - **不問**：技術取捨不出卡（見第 2 條）
   - 已經在跑的背景任務不用取消；背景任務設定成做完自動回報
5. **只在使用者要求時** commit、push、發布。
6. **回覆**：開頭先講結果或要使用者做的事，用繁體中文完整句子；進度放任務清單，不要連發沒人要求的回覆；數字要註明來源。
7. **要求和界線不寫進產品**：使用者的要求、界線、決定的理由是給 AI 看的，不是給產品讀者看的。
   - **介面文字、說明文件、程式註解**只描述產品本身：是什麼、怎麼用。不寫「依使用者要求……」「本功能不提供 X」「注意：不可……」這類轉述對話的句子
   - **做不到或刻意不做的事不用宣告**：沒有計時器就是沒有，不必在畫面上寫「本頁不顯示計時」。只有讀者操作時真的需要知道的限制才寫，而且用讀者的角度寫
   - **程式註解只解釋不明顯的技術原因**，不寫「使用者說不要用 emoji」這種話
   - **要求和理由放在這裡**：規劃文件的定案清單、ADR、`CLAUDE.md`、測試（用測試守住界線，比寫在畫面上有效）
   - **寫之前問一句**：「這句話的讀者需要它嗎？我是在描述產品，還是在轉述對話？」

   | 寫進產品（壞） | 改成 |
   |---|---|
   | 畫面：「依需求，本頁不顯示計時」 | 不寫，直接沒有計時器 |
   | 說明文件：「依使用者明確界線，本工具不會自動提交」 | 不寫；若讀者需要知道，寫「提交需要手動執行」 |
   | 程式註解：`// 使用者要求按鈕用綠色` | 刪掉 |
   | 錯誤訊息：「已依規格停用此功能」 | 「此功能目前無法使用」，或直接不顯示該功能 |

### 決定的分類

| 類型 | 誰定 | 怎麼記 |
|---|---|---|
| 目標、範圍（做不做、做成什麼樣） | 使用者 | 提問卡，選完一句確認，再改規劃文件 |
| 改動使用者原文件指定的東西 | 使用者 | 提問卡，推薦選項附數字理由 |
| 技術取捨 | 主代理 | 「主代理自定」清單，回覆說「我直接定了」 |
| 使用者在討論中認同的替代方案 | 使用者（已定） | 直接寫進規劃文件 |

### 技術取捨：主代理自己定

會影響**怎麼做**、但不改變**做出來的東西長什麼樣、做不做、花不花錢**的決定。

| 類別 | 例子 |
|---|---|
| 架構 | 狀態放前端 store 還是後端；新題型另開資料表，還是沿用現有結構加欄位 |
| 實作方式 | 數學公式用 KaTeX 還是 MathJax；計時器用 `setInterval` 還是用時間戳計算 |
| 順序 | 先做資料模型還是先做匯入；哪一批先做 |
| 門檻、預設值 | 快取過期時間 30 分鐘；重試 3 次；模擬跑 10,000 次 |
| 測試 | 要不要多測一種情況；用單元測試還是離線重播 |
| 命名、檔案位置 | 元件名稱；研究報告放哪個資料夾 |
| 工具、代理分工 | 研究派給哪個代理；用 Playwright 還是手動截圖 |
| 修 bug 的方法 | 改事件處理還是改焦點管理 |

### 要問使用者的

| 類別 | 例子 |
|---|---|
| 目標、範圍 | 要不要支援某個功能；這版要不要做某個考試 |
| 成品長相 | 計時器放哪裡；介面要像原版還是自己設計 |
| 改使用者指定的東西 | 文件寫「用資料集 A」，想改成 B |
| 花錢 | 換成付費 API；實測一次的費用 |
| 對外 | commit、push、發布、寄信、寫入正式站 |
| 無法復原 | 刪檔、刪資料、覆蓋正式站內容 |

**灰色地帶**：問自己「使用者看到結果時，會不會覺得這不是他要的？」會就問；不會（只在意能不能動）就自己定。例如公式渲染套件本來是技術取捨，但如果渲染出來的字型跟原版差很多，就變成成品長相的問題。

技術取捨雖然不問，但每一條都寫進規劃文件的「主代理自定」清單，使用者隨時可以推翻。

## 2. 專案層（第一次在專案用 Agent 時決定）

由 `/setup-project`（改寫自 `setup-matt-pocock-skills`）訪談使用者後，寫進 `docs/agents/`：

| 檔案 | 內容 |
|---|---|
| `docs/agents/workflow.md` | 這個專案的檢查指令、實測方式、部署步驟、代理權重 |
| `docs/agents/issue-tracker.md` | 工單放哪裡（預設：repo 內 `docs/plans/<功能>/`） |
| `docs/agents/domain.md` | `GLOSSARY.md` 與 ADR 的位置 |

`CLAUDE.md` 或 `AGENTS.md` 只加一段 `## Agent skills`，指向上面三個檔案。沒有專案層的專案，skill 一律用預設值，需要專案資訊時才提醒使用者跑 `/setup-project`。

## 3. 角色

| 角色 | 做什麼 | 預設人選（專案層可改） |
|---|---|---|
| 主代理 | 統籌、彙整、改契約、做決定、驗收 | 目前這個 Claude 對話 |
| 研究代理 | 網路查證、官方規格、授權、價格 | Claude（雲端可用時優先） |
| 研究代理（repo） | repo 適配、量化、原型腳本、實際生成比較 | Codex Astra（唯讀） |
| 實作代理 | 照工單和契約寫程式 | 後端：Codex Sol；前端：Claude |
| 審查代理（找） | 唯讀審查，盡量找出問題 | Codex Astra |
| 審查代理（判） | 逐條判級、確認問題是否真的存在、懂得取捨 | Claude Fable |

規則：
- 子代理一律用**全新的 context** 開始，靠路徑指標溝通（規格、工單、研究報告），不要把內容貼進提示
- 子代理的回報只是聲明，主代理要自己驗證之後才算數
- 契約（共用型別、API 介面）只由主代理改

## 4. 各階段

### 4.1 對齊：`/askme`

接住使用者的話：

| 使用者說的 | 要做的 |
|---|---|
| 丟資料、「先開一個串」 | 先讀程式和 docs，回一則「現況三點」 |
| 「為什麼要 X？」 | 直接答：來源（使用者文件寫的，還是我加的）、理由、替代方案。不要順便改東西 |
| 認同替代方案 | 當成定案，馬上改規劃文件，一句回覆確認 |
| 「Brainstorm 一下」 | `brainstorm`：換角度發想、補冷門點子、去重篩選，最後用提問卡讓使用者勾要深入的（研究依據見 `BRAINSTORM-RESEARCH.md`） |
| 「詳細講 X」「展開說明」 | `explain`：一句結論先講，再分段（原本、原計畫、現在怎麼改與為什麼）；不改東西，預設結尾不提問 |
| 「深入研究、分析利弊、提更好的方式」 | 再派一輪研究；結論要說「維持」或「改成 X」，並附數字 |
| 「現在空閒，可以跑」 | 立刻在使用者電腦上跑實驗 |
| 追加條件（「兩個都要測」） | 當場併進正在跑的任務，不重開 |
| 「圖解」「畫給我看」 | 在規劃文件裡加圖，回覆一句講重點和圖的位置 |
| 「訪談我」「Interview me」 | 進入完整訪談模式（見下） |

**完整訪談模式**（借用 Matt 的 grilling，改用提問卡）：

1. 把要決定的事畫成**決策樹**：每個決定底下掛著依賴它的其他決定。
2. **前緣**（frontier）是前置條件都已經定了的決定，也就是現在問不需要猜答案的題目。
3. 一輪出一張提問卡，放前緣上的題目（最多 4 題）；前緣太多就挑最上游的，其他留到下一輪。
4. 只把**使用者要決定的事**放進卡片；技術取捨照第 1 節規則自己定，並在回覆裡列出「這輪我直接定了」。
5. 事實由主代理自己查（讀檔、派子代理），不要問使用者。
6. 前緣清空、所有分支都走過之後，用一句話確認雙方理解一致，再開始動手。

訪談過程中，遇到專有名詞就寫進 `GLOSSARY.md`；遇到難以回頭的決定就寫一份 ADR。

### 4.2 研究：`research`

- 一輪派 4–6 個代理；網路類和 repo 類各半（見第 3 節）
- 主代理只彙整，不自己做研究
- 研究分輪次：使用者丟資料 → 第一輪；Brainstorm 挑方向 → 第二輪；使用者質疑某個設計 → 第三輪；有候選方案、電腦空閒 → 實驗輪

**每個研究任務的提示都要有六項：**

1. **共同背景**：要先讀的檔案、已經定案的決定（逐條列）
2. **唯讀規則**：不改 repo、不 commit、不建置（真的要建置時，照專案層的規則）
3. **產出位置與檔名**：預設 `docs/research/<功能>/<代理>-<編號>-<主題>.md`
4. **要量的東西**：指標、樣本數、對照組
5. **隱私**：使用者資料只做統計，引用原文每段不超過一句，金鑰只從環境變數讀
6. **回報格式**：報告路徑，加上每份 10 行內的重點

每輪結束：更新規劃文件，回覆「結論、改了什麼、（如果有）一件要使用者做的事」。研究需要只有使用者能給的東西時（例如要填表才能下載的資料），回覆開頭寫清楚要使用者做什麼、放到哪個路徑，其他工作照常進行。

### 4.3 規劃：`/to-plan`

產出 `docs/plans/<功能>/spec.md`，章節固定：

1. **摘要**：目標（使用者原話）、三到五句方向
2. **定案清單**：使用者定的、主代理自定的，分開列；每條寫內容、誰定的、日期、一句理由、依據。被推翻的舊決定用刪除線保留，不要直接刪
3. **設計**：資料模型、流程圖、介面、契約
4. **狀態展開**：由 `/expand-states` 填（見 4.4）
5. **批次**：由 `/to-batches` 填（見 4.5）
6. **驗收指標**：數字門檻
7. **未決事項**：誰要做什麼、在等什麼
8. **研究索引**：每份報告的路徑與一行結論

大工程開工前，先跑一次 `/health-check`，問它「怎麼讓這次改動變簡單？」，把結果寫進「設計」一節。

### 4.4 展開狀態：`/expand-states`（新 skill）

實作之前，把每個功能**會遇到的所有狀況**列出來。常見的有：中途換題或換頁、版面變化、網路延遲或斷線、讀取錯誤、載入中、逾時、使用者中途接手、視窗尺寸變化。

每種狀況寫三件事：

| 欄位 | 內容 |
|---|---|
| 偵測 | 怎麼知道進入了這個狀況 |
| 處理 | 程式要怎麼做 |
| 退路 | 處理失敗時怎麼退 |

每種狀況都要對應**一個測試**：

- 邏輯、後端：照 `tdd` 先寫失敗的測試（紅燈 → 綠燈）
- 介面、整合：從現有的錄製或紀錄找畫面，做成離線重播測試；找不到就寫「沒有樣本」，並說明要怎麼人工造出來

狀況清單就是 `tdd` 要測的介面清單，不用再另外跟使用者確認一次。

### 4.5 拆批次：`/to-batches`

把規格拆成工單，放在 `docs/plans/<功能>/tickets/NN-<名稱>.md`。每張工單寫明**被哪些工單擋住**（blocking edges）。

排序原則：

1. **地基先做**：被多個功能共用的先做
2. **省錢的先做**：之後每次實測都要花錢的部分（例如快取）
3. **高風險、要實測的往前**；純介面的往後，或拆出去平行做
4. 每批都要能獨立審查、獨立驗收
5. 預設切成垂直切片（每片從資料到介面都打通，能單獨展示）；大範圍的機械式改名才用「先擴充、再遷移、最後收斂」

可以拆成平行串的：不碰程式碼的研究、介面規格草稿、程式碼互不重疊的批次。要留在同一串依序做的：改到同一批檔案的批次、要用特定機器的工作、要真機實測的工作。

### 4.6 每批一輪：`/implement` 或 `/implement-plan`

- 一張工單、在目前對話做：`/implement`
- 整份規格、多張工單平行做：`/implement-plan`（依工單相依關係，同時派所有已解鎖的工單，各自在自己的 worktree 做，最後合併到一條整合分支）

每批固定走五步：

| 步驟 | 要點 |
|---|---|
| 1. 契約 | 主代理先改共用型別和介面 |
| 2. 實作 | 派實作代理，附上工單、契約、狀況清單和離線測資的路徑 |
| 3. 審查 | `/plan-review`（見 4.6.1）；**必修全修**才進下一批 |
| 4. 檢查 | 跑專案層定義的檢查指令；失敗只重跑失敗的部分 |
| 5. 實測 | 照專案層的實測方式；學到的事補回專案的實測文件 |

`/implement-plan` 一個指令就把整份計畫做完，過程中不用使用者管；每批結束都附一份成果報告（見 4.6.2）。只有遇到第 1 節的四類事情，或審查第 2 輪還有必修時，才停下來出提問卡。

#### 4.6.1 審查：`/plan-review`

原本「全部修完才進下一批」會修不完：審查者看到什麼就報什麼，修完再審又冒出新的小問題，越細心的審查者越停不下來。改成以下規則：

1. **先定範圍**：只看這批的改動，對照計畫的驗收指標。範圍外的問題寫進「下次再說」清單。
2. **每條都要寫出會壞的具體情境**（什麼輸入或狀態 → 錯誤結果）。寫不出來的自動降級。
3. **找問題和判級分開**：Astra 盡量找；Fable 逐條判級，並確認問題是不是真的存在。
4. **分三級**：

   | 級別 | 什麼算 | 怎麼處理 |
   |---|---|---|
   | 必修 | 會壞、違反計畫、資料遺失、安全問題、把要求或界線寫進產品（見第 1 節第 7 條） | 這批一定修 |
   | 建議 | 品質可以更好，但不會壞 | 順手能改就改，不擋進度 |
   | 小毛病 | 命名、風格、個人偏好 | 不修，只記下來 |

5. **停止規則**：必修修完後，只審**修改過的部分**，最多 2 輪。第 2 輪還有必修，停下來出提問卡問使用者。
6. **交給回顧**：建議和小毛病交給 `/retro`；同一類反覆出現，就變成規範或自動檢查。

保留 Matt 的雙軸：Astra 找問題時分兩個面向報告，「符合規範」和「符合計畫」，避免一邊掩蓋另一邊。

#### 4.6.2 成果報告

每批結束給使用者一份看得懂、不用讀程式碼的 **HTML 報告**（借 `/health-check` 的報告樣式：前後對照圖、達成狀況用標籤顯示；視覺主題用 fa-study-kit），同時把重點記進規劃文件：

1. **一句話結果**：這批做完了什麼
2. **前後對照**：截圖、數字、實測紀錄
3. **驗收指標**：逐條寫達到、沒達到，附數字
4. **審查**：必修幾條、全修了沒有；建議與小毛病幾條，放到哪裡
5. **還沒做的**：以及下一批是什麼
6. **要使用者做的事**：如果有，只寫一件

### 4.7 回顧：`/retro`

在同一個對話裡、清空 context 之前跑。建議改進的是**環境**，不是程式碼：

- 機械式的錯誤 → 變成自動檢查
- 判斷上的錯誤 → 變成程式規範（`/plan-review` 會照著審查）
- 使用者的偏好與糾正 → 寫進記憶（附 Why 和 How to apply）
- 實測學到的事 → 補進專案的實測文件

## 5. 輔助工具

| 工具 | 什麼時候用 |
|---|---|
| `prototype` | 有設計問題光靠討論答不出來時，寫一個用完就丟的原型 |
| `/handoff` | 換工具、換資料夾、交給別人，或在階段中途拆出支線 |
| `/wait-what` | 看不懂 AI 剛剛說什麼時，請它用白話和詞彙表重講 |
| `/health-check` | 有空時跑，或大工程開工前跑；產出 HTML 報告，列出程式碼可以改善的地方與前後對照圖，挑一個再回到 `/askme` |
| `/to-questionnaire` | 卡在別人腦中的資訊時，產生一份問卷給對方填 |
| `wizard` | 只能人工做的步驟（金鑰、DNS、主控台），做成一步步帶你走的腳本 |
| `pr` | 開 PR 時的內文格式：最小的視覺說明、前後對照證據、可否回頭 |
| `/teach` | 跨多次對話學一個新概念 |
| `/triage` | 處理別人開的 issue |

### 階段之間的五種選擇

1. **繼續**：什麼都不做，預設先考慮這個
2. **`/clear`**：接下來的事跟現在完全無關
3. **`/handoff`**：要換工具、換資料夾、交給別人
4. **子代理**：範圍很清楚的任務，派出去只拿回報告
5. **`/compact`**：context 太長（約 150k tokens 以上）時，在階段邊界壓縮
